# CLAUDE.md — Ward & Fall (ورد وفل)

## Project purpose
A bilingual (AR/EN) flower-shop marketing site + frontend admin dashboard
prototype, for a real shop whose product photography includes garden rose
bouquets, mixed-flower arrangements, gift wrapping, and celebration cakes.
No backend yet — this phase is UI only, structured so Supabase can be
plugged in later without a rewrite.

## Architecture decisions
- React 19 + TypeScript + Vite + Tailwind CSS v4 (`@tailwindcss/vite`)
- React Router for pages, react-helmet-async for SEO
- LEGO-style component architecture: `components/{layout,navbar,footer,hero,
  categories,products,product-card,testimonials,contact,ui}`
- `data/mockProducts.ts` + a `productService` abstraction — swap to Supabase
  later without touching UI components
- No cart, no checkout, no payment gateway. WhatsApp click is the
  conversion event, generated by one pure helper: `createWhatsAppOrderLink(product)`

## Design direction (deliberately different from a generic purple wreath look)
Named **"Atelier Bloom"** — an editorial floral-boutique direction built from
the shop's actual photography (deep crimson garden roses, cream mums, black
ribbon, gold cake boards, blush storefront) rather than a flat lavender
palette. Full token spec in `BRAND_GUIDELINES.md`.

## Current implementation phase
**Phase 3 — Admin dashboard (frontend, mock data layer).** Storefront
(Phase 2) complete. Admin dashboard built at `/admin`: layout (sidebar +
topbar), dashboard overview, products CRUD (list/add/edit/delete, search,
category/status filters, toggle active/featured), categories CRUD, and
placeholder Orders/Customers/Settings pages with honest empty states.

**Not yet done:** live Supabase connection (no project credentials
available in this environment — see "Supabase" below), image upload is a
local-preview mock, Settings fields don't persist.

## Routes
- `/` — storefront (Home)
- `/admin` — dashboard overview
- `/admin/products` — product list/table
- `/admin/products/new` — add product
- `/admin/products/:id/edit` — edit product
- `/admin/categories` — categories CRUD
- `/admin/orders` — orders (empty state, no fake data)
- `/admin/customers` — customers (empty state, no fake data)
- `/admin/settings` — store settings (UI only, not persisted)

## Data flow
`productService` / `categoryService` (`src/services/productService.ts`) are
the only things dashboard pages and (eventually) the storefront call for
product data — never `seedAdminData.ts` directly from a page. Today they
read/write `localStorage` with simulated latency, seeded from
`seedAdminData.ts`. Swapping to Supabase means rewriting only the bodies of
these service functions; call sites don't change.

## Supabase — CONNECTED (live)
Project `aspqohlunqyjvgduqwrm` (region eu-central-1), connected via
`.env.local` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` — the
legacy `anon` JWT key, not the oddly-labeled "publishable" key that
described itself as `service_role` in the dashboard — that one was
deliberately not used).

Tables live: `categories`, `products`, `customers`, `orders`, `order_items`.
RLS enabled on all five. Storage bucket `product-images` live (public read,
authenticated write, 5MB limit, image mime types only).

`productService` / `categoryService` / `orderService` / `customerService`
(`src/services/*.ts`) now call Supabase directly — no mock/localStorage
layer remains. `src/lib/supabase.ts` is the single client instance.
`src/types/database.ts` mirrors the live schema (must include `Views`,
`Functions`, `Enums`, `CompositeTypes`, and each table's `Relationships`
key — omitting these silently degrades `insert`/`update` generics to
`never` under `tsc -b`, which was a real bug hit and fixed in this project).

## Auth
Supabase Auth (email/password) gates `/admin/*` via `AuthContext` +
`AdminLayout`'s session check → redirects to `/admin/login`. One admin
account exists (created directly via SQL with pgcrypto since no
dashboard-equivalent "create user" tool was available in this
environment): `admin@wardandfall.com` — **share/rotate this password
through a private channel, not committed anywhere in this repo.**

## Routes
- `/` — storefront (Home), reads live `active=true` products/categories
- `/admin/login` — Supabase Auth sign-in
- `/admin` — dashboard overview (real stats)
- `/admin/products`, `/admin/products/new`, `/admin/products/:id/edit`
- `/admin/categories`, `/admin/orders`, `/admin/customers`, `/admin/settings`

## Current limitations
- Settings page fields are still visual-only (not persisted to a
  `store_settings` table — not yet built).
- Orders/Customers pages read real (currently empty) tables — no
  manual order-entry UI yet.

## Scope boundaries
No database, no auth backend, no API, no payment, no online checkout —
current phase and next several phases (per original spec) are frontend only.

## Responsive requirements
Mobile-first; verified breakpoints: 320, 375, 480, 768, 1024, 1440, 1920px+.
Max-width container prevents ultrawide stretch.

## RTL/LTR requirements
Centralized language system (not manual mirroring); `dir` attribute switches
at the document root; persisted in `localStorage`.

## Dark/light mode requirements
Intentional dark palette (see tokens) — not an inverted light palette.
Persisted in `localStorage`.

## WhatsApp ordering architecture
Single source of truth: `utils/createWhatsAppOrderLink.ts`. Number stored
once, formatted to international `963` form for the `wa.me` link only.

## Dashboard architecture
Frontend-only CRUD over mock state; `Products`, `Add/Edit Product` (shared
`ProductForm`), `Categories`, `Settings`, sidebar → drawer on mobile.

## Future Supabase integration plan
`productService` mock implementation today; same call signatures line up
with a future Supabase-backed implementation. No fake DB behavior modeled.

## Important design decisions
- Palette is derived from real product photos, not the logo's lavender
  wreath alone — the logo remains used as the literal brand mark, but the
  site's dominant palette is rose/ink/gold on warm ivory.
- No emoji-as-icon; Lucide React only.
